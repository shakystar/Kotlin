# Kotlin 디자인 패턴 학습

디자인 패턴은 반복되는 설계 문제에 대해, 특정 상황에서 사용할 수 있는 해결 구조를 정리한 것이다. 코드 모양을 외우기보다 어떤 문제를 해결하고, 객체의 책임과 관계를 어떻게 바꾸며, 어떤 비용을 만드는지 이해한다.

## 학습 관점

패턴을 적용하는 것 자체가 목표는 아니다. 지금 무엇이 변경하기 어렵고, 이 구조가 그 어려움을 줄이는지를 먼저 생각한다. 클래스와 파일이 늘어나는 비용이 해결하려는 문제보다 클 수도 있다.

패턴은 상황, 문제, 해결 구조, 결과와 비용을 함께 설명한다. 이름은 문제 자체뿐 아니라 연결·장식·대리 같은 해결 방식이나 역할을 나타내기도 한다. 비슷한 구현도 설계 목적에 따라 다른 패턴으로 분류될 수 있으며, 구조가 항상 같다는 뜻은 아니다.

각 예제에서 다음을 확인한다.

- 어떤 상황에서 무엇이 불편해지는가?
- 패턴 없이 구현하면 어느 코드가 함께 바뀌는가?
- 객체의 책임과 관계를 어떻게 나누었는가?
- 어떤 변경이 쉬워지고, 어떤 복잡성이 늘었는가?
- 더 단순한 방법으로도 충분한가?

## 현재 학습한 예제

현재 구현된 예제를 나열한 목록이며 모든 디자인 패턴을 다룬 것은 아니다. 단순 팩토리는 GoF 23개에 포함되지 않는 비교용 예제다.

| 분류 | 패턴 | 해결하려는 문제 |
|---|---|---|
| 생성 | [싱글턴 (Singleton)](src/main/kotlin/creational/singleton/README.md) | 여러 곳에서 동일한 상태나 객체를 공유해야 하는데, 호출할 때마다 새 객체를 만들면 서로 다른 상태를 보게 된다. |
| 생성 | [단순 팩토리 (Simple Factory)](src/main/kotlin/creational/factory/simple/README.md) | 종류에 따른 객체 생성 분기가 여러 사용처에 흩어져, 생성 방법을 바꿀 때 같은 조건문을 반복해서 수정해야 한다. |
| 생성 | [팩토리 메서드 (Factory Method)](src/main/kotlin/creational/factory/method/README.md) | 공통 처리 흐름은 유지하면서, 그 흐름에서 사용할 객체의 생성 방법을 하위 클래스가 확장해야 한다. |
| 생성 | [추상 팩토리 (Abstract Factory)](src/main/kotlin/creational/factory/abstractfactory/README.md) | 버튼과 체크박스처럼 관련된 객체들을 제품군별로 생성하면서, 사용하는 코드가 구체 테마 클래스에 의존하지 않게 해야 한다. |
| 생성 | [빌더 (Builder)](src/main/kotlin/creational/builder/README.md) | 필수 값과 여러 선택 사항을 조합해 객체를 완성할 때, 생성 과정과 완성된 객체를 사용하는 책임을 분리하고 싶다. |
| 생성 | [프로토타입 (Prototype)](src/main/kotlin/creational/prototype/README.md) | 기존 객체의 설정을 바탕으로 일부만 바꾼 새 객체가 필요할 때, 생성 인자를 다시 나열하지 않고 복제하고 싶다. |
| 구조 | [어댑터 (Adapter)](src/main/kotlin/structural/adapter/README.md) | 외부 라이브러리가 제공하는 인터페이스와 우리 업무 코드가 요구하는 인터페이스가 다르다. 업체별 호출 방식이 업무 코드에 퍼지는 것을 줄이고 싶다. |
| 구조 | [데코레이터 (Decorator)](src/main/kotlin/structural/decorator/README.md) | 로그와 접두사 같은 선택 기능을 조합할 때마다 기존 클래스를 수정하거나 모든 조합에 해당하는 하위 클래스를 만들고 싶지 않다. |
| 구조 | [프록시 (Proxy)](src/main/kotlin/structural/proxy/README.md) | 호출자가 실제 문서에 바로 접근하면 조회 권한을 일관되게 검사하기 어렵다. 실제 객체를 대신하는 접근 지점에서 허용 여부를 판단하고 싶다. |

## 어댑터·데코레이터·프록시 비교

세 패턴 모두 다른 객체를 감쌀 수 있지만 목적을 구분한다.

| 패턴 | 중심 목적 | 이 저장소의 예제 |
|---|---|---|
| 어댑터 | 다른 인터페이스를 우리 규칙에 연결 | 업체별 이메일 API를 Notifier로 연결 |
| 데코레이터 | 같은 인터페이스를 유지하며 기능 조합 | 알림에 로그와 접두사 추가 |
| 프록시 | 실제 객체에 대한 접근 관리 | 권한이 있을 때만 문서 조회 |

원본을 호출하면 데코레이터이고 막으면 프록시인 것은 아니다. 호출 여부 하나보다 해결하려는 문제를 본다. Python의 데코레이터 문법이나 Java의 프록시 기능과도 구분한다. 패턴은 언어에 종속되지 않는 설계 방법이며 언어 기능은 그 방법을 표현하는 수단이 될 수 있다.

## 문서 구성

각 예제 README는 다음 여섯 항목을 같은 순서로 사용한다.

1. 해결하려는 문제
2. 패턴 없이 구현하면
3. 이 예제의 해결 방식
4. 실행과 확인
5. 장점과 비용
6. 적용할 때와 쓰지 않아도 될 때

현재 코드에서 관찰할 수 있는 동작과 추가 실험을 구분한다. 새 패턴을 공부할 때는 [README 템플릿](README.template.md)을 복사하고, 예제 코드에 맞게 채운다.

## 실행 방법

이 저장소는 각 예제를 독립적으로 컴파일하는 학습 환경이다. VS Code에서 저장소 루트인 Kotlin 폴더를 연다.

- JDK와 `java` 명령이 필요하다. 현재 환경은 JDK 17을 사용한다.
- 실행 스크립트는 저장소 루트의 `.tools/kotlin-2.4.21/kotlinc/bin/kotlinc`를 사용한다. 이 도구 폴더는 Git에 포함되지 않으므로 다른 환경에서는 별도로 준비하거나 스크립트 경로를 조정한다.
- 해당 예제의 `Main.kt`를 열고 파일들을 저장한 뒤 `⌘ + Shift + B`를 누른다.
- 작업은 현재 파일 위치에서 가장 가까운 상위 `Main.kt`를 찾고, 그 폴더와 하위 폴더의 Kotlin 파일만 컴파일한다.
- 실행 결과물은 임시 폴더에 생성되고 실행 종료 후 정리된다.

설정은 [tasks.json](../.vscode/tasks.json)과 [run-kotlin.sh](../.vscode/run-kotlin.sh)에 있다. 터미널에서 실행하려면 저장소 루트에서 다음처럼 호출한다.

```bash
/bin/bash .vscode/run-kotlin.sh "$PWD" "$PWD/patterns/src/main/kotlin/structural/proxy"
```

각 예제의 실행 진입점은 하나로 유지한다. 다른 예제에는 같은 이름의 클래스와 main 함수가 있으므로 전체 소스 폴더를 한 번에 컴파일하지 않는다. 앞으로 하나의 Gradle 빌드로 묶는다면 패키지와 모듈 경계를 별도로 정리한다.

## 예제의 범위

이메일 전송, 가입, 화면 표시 등은 콘솔 출력으로 동작을 관찰하는 모형이다. 실제 외부 API, DB, 인증 서버는 연결하지 않았다. 백엔드에 적용할 때는 실제 업무 규칙과 의존성, 실패 처리, 동시성 요구에 맞게 설계를 선택한다.
