# 싱글턴 (Singleton)

[전체 학습 안내](../../../../../README.md)

## 해결하려는 문제

여러 곳에서 동일한 상태나 객체를 공유해야 하는데, 호출할 때마다 새 객체를 만들면 서로 다른 상태를 보게 된다.

## 패턴 없이 구현하면

각 기능에서 상태 객체를 따로 만들면 한 곳에서 바꾼 값이 다른 곳에 반영되지 않는다. 하나의 인스턴스를 생성해 필요한 곳에 전달하는 방법도 가능하다. 싱글턴은 단일 인스턴스와 접근 지점을 제공하는 선택이다.

## 이 예제의 해결 방식

| 파일 | 역할 |
|---|---|
| [SharedState.kt](SharedState.kt) | `object`로 선언한 공유 객체. 사용자 이름, 개수, 로그인 상태를 보관한다. |
| [State.kt](State.kt) | `State<T>`는 타입별 값을 담는 일반 클래스이며 싱글턴이 아니다. |
| [Main.kt](Main.kt) | 공유 객체의 값을 변경하고 읽는다. |

`Main → SharedState → State<T>.value`

## 실행과 확인

[Main.kt](Main.kt)를 저장한 뒤 VS Code에서 열고 `⌘ + Shift + B`로 실행한다. 환경 준비는 [전체 학습 안내](../../../../../README.md)를 참고한다.

현재 코드의 출력:

```text
테스트명
10
```

현재 예제는 사용자 이름과 개수를 변경해 출력한다. 같은 객체인지 직접 비교하려면 두 변수에 `SharedState`를 대입한 뒤 `===`로 확인한다. 이 비교는 현재 Main에는 포함되어 있지 않다.

## 장점과 비용

공유할 객체를 일관되게 찾을 수 있다. 대신 전역의 변경 가능한 상태는 의존성을 숨기고 테스트 사이에 영향을 줄 수 있다. `object`의 초기화 안전성이 내부 `var`의 동시 변경까지 안전하게 만들지는 않는다.

## 적용할 때와 쓰지 않아도 될 때

실제로 하나만 공유해야 하는 객체에 적용한다. 객체를 생성자로 전달하면 충분하거나 사용자·요청별 상태라면 싱글턴으로 만들 필요가 없다. 별도 프로세스로 실행되는 마이크로서비스 사이에는 이 값이 공유되지 않는다. `val`은 객체 재대입을 막지만 내부 `var value`의 변경은 허용한다.
