# 빌더 (Builder)

[전체 학습 안내](../../../../../README.md)

## 해결하려는 문제

필수 값과 여러 선택 사항을 조합해 객체를 완성할 때, 생성 과정과 완성된 객체를 사용하는 책임을 분리하고 싶다.

## 패턴 없이 구현하면

긴 위치 인자 목록은 각 값의 의미를 읽기 어렵다. 다만 Kotlin에서는 이름 있는 인자와 기본값만으로 이 문제를 상당 부분 해결할 수 있다.

## 이 예제의 해결 방식

| 파일 | 역할 |
|---|---|
| [Order.kt](Order.kt) | 완성된 주문. `init`에서 상품명, 양수 수량, 배송지를 검증한다. |
| [OrderBuilder.kt](OrderBuilder.kt) | 필수 값을 받고 선택 값을 모은다. 설정 메서드는 `this`를 반환하고 `build()`가 주문을 만든다. |
| [Main.kt](Main.kt) | 빌더로 주문을 만들고 예외를 메시지로 처리한다. |

`OrderBuilder(필수 값) → giftWrap() → request() → build() → Order.init 검증`

## 실행과 확인

[Main.kt](Main.kt)를 저장한 뒤 VS Code에서 열고 `⌘ + Shift + B`로 실행한다. 환경 준비는 [전체 학습 안내](../../../../../README.md)를 참고한다.

현재 코드의 출력:

```text
키보드
true
문 앞에 놓아주세요
```

현재 수량은 2이므로 주문이 정상 생성된다. 추가 실험으로 수량을 0으로 바꾸면 `catch`가 `주문 실패 : 수량은 1개 이상이어야 해요.`를 출력한다. 검증은 빌더가 아닌 `Order`에 있어 직접 생성해도 적용된다.

## 장점과 비용

구성 단계를 분리하고 체이닝으로 선택 사항을 표현한다. 대신 별도 클래스와 변경 가능한 중간 상태가 생긴다. 검증은 빌더만의 장점이 아니다. 현재 코드는 간단한 fluent builder이며, 별도의 Director로 조립 순서를 관리하는 형태까지 구현한 것은 아니다.

## 적용할 때와 쓰지 않아도 될 때

생성 과정이 여러 단계이거나 중간 구성을 모아 마지막에 완성할 필요가 있을 때 적합하다. 지금처럼 단순한 데이터 객체라면 Kotlin의 이름 있는 인자와 기본값이 더 간단할 수 있다.
